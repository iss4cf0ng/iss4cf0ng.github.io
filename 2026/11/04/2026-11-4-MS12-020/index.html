Introduction

This article is part of my From Bug To Exploit series.

In this article, I will introduce MS12-020, a security update that addresses two vulnerabilities in the Remote Desktop Protocol (RDP). This is also my first time performing Windows kernel debugging.

MS12-020

MS12-020 is a Microsoft security bulletin that addresses two vulnerabilities:

  1. CVE-2012-0002
  2. CVE-2012-0152

Both vulnerabilities are related to the Remote Desktop Protocol (RDP).

The first vulnerability, CVE-2012-0002, could allow an attacker to execute arbitrary code on a vulnerable system. However, I have not been able to find a working exploit that I can reproduce in my own lab. Since I could not reproduce it myself, I decided not to investigate this vulnerability further in this article.

Instead, I will focus on the second vulnerability, CVE-2012-0152, which can cause a Denial-of-Service (DoS) condition by triggering a Blue Screen of Death (BSoD).

This is also my first time using WinDbg to perform Windows kernel debugging.

How RDP Works

The Remote Desktop Protocol (RDP) is a proprietary protocol developed by Microsoft that allows users to connect to and interact with a remote computer over a network.

If you remember, I released DuplexSpy v2.0.0 in January. One of its features allows users to remotely view and interact with a desktop:

Although DuplexSpy also provides an interface for controlling the remote mouse and keyboard, its underlying mechanism is quite different from RDP.

The DuplexSpy payload (client) captures real-time data, including screenshots and cursor coordinates. It then packages this data into chunks and sends them to the C2 server. In addition, the payload asynchronously receives cursor coordinates and keyboard input from the C2 server and applies them to the remote system.

RDP has a much more sophisticated mechanism. It provides a remote desktop experience and supports authentication, making it commonly used for remote system administration.

RDP is commonly used to administer Windows servers, although it can also be enabled on personal computers.

The implementation of RDP is quite complicated.

Root Cause of the Vulnerability

The root cause of the MS12-020 DoS vulnerability is a Use-After-Free (UAF).

C and C++ do not provide automatic garbage collection by default, unlike languages such as Java and C#. Therefore, when a program dynamically allocates memory on the heap, the developer is generally responsible for managing its lifetime and releasing it when it is no longer needed.

For example:

However, mistakes can happen. As a program becomes more complex, developers may accidentally release the same memory more than once.

This is known as a Double Free vulnerability. Depending on the memory allocator and execution environment, attempting to free the same memory twice may cause a crash or other unexpected behavior.

On the other hand, a developer might accidentally continue using a pointer after the memory it references has been freed.

This is known as a Use-After-Free (UAF) vulnerability.

Once memory has been freed, the program must no longer access it through the old pointer. However, the pointer itself does not automatically become invalid or change to NULL. If the program continues to use it, the result is undefined behavior. Depending on the circumstances, this may lead to memory corruption, a crash, or potentially exploitable behavior.

Some publicly available proof-of-concept implementations and analyses of MS12-020 discuss different possible causes, including Double Free and Use-After-Free behavior.

In this article, I will focus on reproducing the second scenario: Use-After-Free.

Windows is a complicated operating system. Multiple drivers and user-mode components work together to provide its features. In other words, RDP functionality is not implemented by a single driver or program. Instead, it involves multiple components that communicate with one another.

The DoS vulnerability discussed in MS12-020 occurs in the RDPWD.sys driver.

Microsoft’s RDP implementation uses a mechanism called a channel. You can think of a channel as a logical communication path within an RDP connection.

During my analysis, I found that the functions RDPWD!_SListRemove and RDPWD!DetachUser do not handle certain pointers and request safely. An attacker can craft malicious connection requests that cause multiple connections using different usernames to be associated with the same channel ID. When these connections are subsequently disconnected, RDPWD!_SListRemove may access a pointer to memory that has already been freed, resulting in a Use-After-Free (UAF) condition.

As the name suggests, ExAllocatePoolWithTag allocates a block of pool memory of the specified size. In this case, the requested allocation size is calculated from the value at offset 0x04, shifted left by four bits. This suggests that the function allocates a larger buffer to accommodate more elements.

Second, the for loops copy data from the original buffer into the newly allocated buffer. The function then frees the original buffer after copying the data.

Based on these observations, it is reasonable to infer that this function expands the buffer’s capacity and that param_1[1] represents the capacity.

These operations suggest that SList implements a circular buffer. The index wraps around to zero when it reaches the capacity, which is a common technique for implementing circular buffers.

Note: I couldn’t find any documentation explaining why Microsoft chose to implement this data structure as a circular buffer. Personally, I suspect that it has something to do with time complexity.

In SListRemove, when a specified element is removed, the last element is moved into the vacated slot. This allows the removal operation to be performed in constant time, or O(1), assuming the element’s index is already known. Since the order of the elements does not need to be preserved, they can still be stored sequentially in the buffer without requiring the remaining elements to be shifted.

In theory, we could also implement this using a singly linked list or a doubly linked list. However, I am not sure whether either approach would be more efficient in this particular scenario.

Based on this behavior, I suspect that param_1[2] represents the head index.

As for param_1[3], it is initialized to 0xFFFFFFFF in SListInit and assigned the same value in SListRemove. Based on these observations, I suspect that it serves as a flag or sentinel value, although its exact purpose requires further investigation.

Finally, param_1[4] initially contains an address offset. Based on how the field is accessed and updated, I believe it stores a pointer to the actual data buffer.

Denial-of-Service

Finally, let’s take a look at how MS12-020 can lead to a denial-of-service condition.

As I mentioned earlier, the server (or, more specifically, the driver) does not properly validate the relationship between a user ID and its assigned channel ID. As a result, multiple users can end up being associated with the same channel ID. When these users disconnect, the server may attempt to access a pointer that has already been freed during the first user’s disconnection.

Consequently, the server may access invalid memory in kernel mode, triggering a Use-After-Free condition and eventually causing a BSoD. This is the root cause of the denial-of-service vulnerability in MS12-020.

Conclusion

This is my first time performing kernel debugging, and I have to say that the internal mechanisms of RDP are extremely complicated. Fully understanding how everything works is quite challenging. However, once we understand these mechanisms, we can start identifying potential vulnerabilities.

Historically, RDP has had many security vulnerabilities, including several RCE vulnerabilities. One example is EsteemAudit, which I would also like to analyze in a future article!

Honestly, I don’t think my analysis is perfect, and there are still many details I haven’t fully figured out. If I discover anything new, I’ll share it in future articles as well!
