Introduction

In this article, I will introduce Heartbleed, a famous vulnerability in OpenSSL discovered in 2014.

Heartbeat and Heartbleed

The OpenSSL Heartbeat extension is an extension to the TLS/DTLS protocols. According to RFC 6520, this extension allows endpoints to keep a connection alive without performing a renegotiation. It can also be used as a basis for Path MTU (PMTU) discovery in DTLS.

In short, the Heartbeat extension allows one endpoint to check whether the other endpoint is still responsive by sending a simple request, without having to renegotiate the connection.

In 2014, researchers discovered a bug in OpenSSL’s implementation of this extension. OpenSSL versions 1.0.1 through 1.0.1f were affected by this vulnerability. The implementation did not properly validate the length specified in Heartbeat requests, allowing remote attackers to read parts of a process’s memory by sending specially crafted packets. This vulnerability became known as Heartbleed.

The vulnerability was named Heartbleed.

Murmur: A creative name, right?

One of the most concerning targets was HTTPS servers. We know that HTTPS protects communication between users and servers by encrypting the data exchanged between them. However, Heartbleed could allow an attacker to read sensitive information from a server’s memory, potentially including session cookies, authentication credentials, and other confidential data.

If an attacker obtained a valid session cookie or other authentication material, they might be able to impersonate a legitimate user and potentially gain administrative access, depending on the information exposed and the application’s security mechanisms.

In this article, I will demonstrate how Heartbleed works.

Cause of the Vulnerability

The vulnerability was caused by a flaw in the implementation of the tls1_process_heartbeat function in ./ssl/t1_lib.c.

The idea behind a Heartbeat request is straightforward: a client sends a payload and specifies its length, and the server responds by sending the same payload and length back to the client.

The vulnerability lies in how the server handles the payload length.

First, the tls1_process_heartbeat function retrieves the payload length from the packet using the n2s macro. It then allocates a response buffer based on the specified length and copies data from the input buffer using memcpy, without verifying that the specified length matches the actual amount of payload data received.

Ideally, the server should copy only the payload data that was actually received. However, an attacker can specify a payload length that is larger than the actual payload. Since the function does not validate this length against the amount of data available in the received packet, memcpy reads beyond the end of the actual payload and copies additional bytes from the process memory into the response buffer. This results in a buffer over-read.

Because the server process may also handle other requests and store sensitive information in memory, the leaked data can potentially include confidential information, such as session cookies, authentication credentials, or other data left in memory.

This is the fundamental cause of Heartbleed: the server trusts the payload length supplied by the peer without checking whether that amount of data is actually available in the received message.

Conclusion

This article demonstrates how a memory disclosure vulnerability can lead to further attacks. In a real-world scenario, the consequences could be even more serious if other sensitive information, such as authentication credentials or private keys, were exposed.
